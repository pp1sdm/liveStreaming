动手前必须先问运营的五个问题

这五个都是 go / no-go，答案不同会导致架构和排期完全不同。建议在写第一行代码之前，带着这五个具体问题去联系抖音开放平台的对接运营。

01
关键词能配单个字母吗？ 官方文档里的关键词示例都是 123、攻击 这类多字符指令。单字母 a 是非常规用法，可能有最短长度限制，或被审核判定为无意义配置。这条不过，整个方案要重做。
02
关键词是随包体固定的，还是后台能随时改？ 如果是随包体提交审核后固定，那 8 个关键词一旦上线就永久绑定，题目必须全部围绕 ABCD 设计。如果有后台可热改，就多一条退路。
03
「官方题库必选」是必须用官方题库，还是「要用才申请」？ 官方文档里答题类玩法标注了「直播玩法官方题库」为必选能力。如果被理解成答题玩法必须跑官方题库，那自定义韩语题就不成立。这是第二大阻塞点。
04
直播形态必须是小玩法客户端 exe 吗？还能用 OBS 吗？ 能力清单里有「玩法客户端（exe）」为必选，数据流是「推送到开发者服务器 → 客户端展示效果」。这意味着画面可能必须由小玩法窗口渲染，而不是你自由搭的 OBS 场景，而且可能需要一台公网服务器。这决定了呈现层是写 HTML 还是写桌面窗口。
05
关键词匹配区分大小写吗？ 如果不区分，a 和 A 只占 1 个配额，8 个关键词可以压缩成 4 个，省下的配额留给「不会」「跳过」这类辅助指令。如果区分，就维持 8 个。

核心闭环

一场直播就是无限循环这五步。主播只控两个动作：开题、公布，其余自动。

答案判定流水线

关键词是模糊匹配，所以官方推给你的远不止答案。判定必须在本地做，而且要严格。

      • engine · 轮次状态机 / 判定流水线 / 计分

      • 若是 exe · Rust 桌面窗口 + 内嵌 webview，复用同一套 HTML

      • 答对即时反馈 · 判定成功立刻滚动显示「昵称 选了 B」，这是留人的关键

    • 06主播控制台
      • 出题 / 封盘 / 公布 / 跳过 / 手改判定

      • 题库 · CSV/JSON 导入，标签 + 难度 + 答案二次确认

      • 答对率 / 答对榜 / 连对 streak

      • 卡点题 · 正确率长期偏低的题回炉
    • 08合规风控
      • 全程只跑服务，不带货已定

落地顺序

关键变化：资质是一条长线，所以本地开发和资质申请必须并行，不能串行。真正依赖官方接口的只有最后一层 WebSocket 接入。

M0 · 现在
骨架 + mock 弹幕源 + 判定流水线 workspace 拆分，MockSource 按剧本吐弹幕（含 Ｂ、haha、「我选B」这些边界样本）， overlay 页能看到题目、四宫格选项、倒计时、答对滚动条。全程不碰抖音，先把判定和画面做对。
M0 ∥ 并行
启动资质与对接 先带「必问 01」联系运营确认单字母关键词能否配置——这一条不过，后面全部作废。 确认可行后，立刻定玩法名并申请软著（可考虑加急），这条线最长且完全在你控制之外。
M1
题库 + 计分 + 落库 导入 200 条 TOPIK 初级题，答案二次确认；实现轮次状态机、答对榜、连对 streak、选项分布，写 SQLite。
M2
控制台 出题 / 封盘 / 公布 / 跳过 / 手改判定，快捷键与脚踏板，实时判定流，开播自检。
M3
接官方 OfficialSource 资质下来后实现真实的 WebSocket 接入、token 自动刷新、断线重连。若「必问 05」确认大小写不敏感，关键词从 8 个压到 4 个。 此时才第一次接触真实弹幕，前面所有逻辑都已在 mock 上验证过。
M4
试播调优 用「疑似」日志看判定准确率和漏判率，调整题目文案与选项长度，跑通真实的节奏感。
